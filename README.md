# gyro-denoise-benchmark

**Does a neural network clean up gyroscope data better than a classical filter? For this problem, no.**
A tuned moving average scored an RMSE of 0.064. A 1D convolutional denoiser scored 0.110 — about 71% worse, on every one of 100 test signals.

Getting to a trustworthy answer meant finding and fixing three bugs in my own method. Each one had quietly made the network look better than it was. Those bugs are the most useful part of this repository.

## Where this comes from

This extends the filtering work in my MSc by Research thesis, *Geolocation of Objects Using MEMS Sensors and GPS* (SSST / University of Buckingham, Distinction).

The thesis built an embedded system that locates a distant object by triangulating two sightlines. Triangulation needs accurate tilt angles, and a small angular error turns into metres of error at the target. Mounted on a quadcopter, the MPU-6050 gyroscope picks up motor vibration, so the raw angle is too noisy to use directly.

To deal with that, the thesis compared four classical filters — Kalman, exponential moving average, Bessel, and Savitzky-Golay — and concluded that the Kalman filter gave the best balance of smoothness and responsiveness for real-time use. That work was published as:

> Kriještorac, M. (2025). *Filtering MEMS Gyroscope Data: A Comparative Analysis of Noise Reduction Methods.* 24th International Symposium INFOTEH-JAHORINA, IEEE Xplore.

The thesis never asked whether a learned filter could do better. This repository asks that question, and answers it.

## The data

500 recorded samples of tilt angle from the MPU-6050, captured on the quadcopter with all four motors running, from the thesis experiment. The drone tilts down toward a target and returns — one rise and one fall, peaking at 8.75°.

The classical filters here are the ones compared in the paper, using its published design parameters, including the 100 Hz design sampling rate specified for the Bessel filter.

**There is no ground truth.** Nobody measured the true tilt at each sample. This shapes everything below.

## Results

100 held-out synthetic test signals. Every method runs forward and backward, so the comparison measures noise removal and not time lag. Lower RMSE is better.

| Method | RMSE | 95% confidence interval |
|:---|---:|:---|
| **Moving average (window 21)** | **0.0644** | 0.0606 – 0.0687 |
| Bessel (4th order, 4 Hz) | 0.0666 | 0.0627 – 0.0705 |
| Butterworth (4th order, 2 Hz) | 0.0671 | 0.0633 – 0.0711 |
| EMA (α = 0.2) | 0.0759 | 0.0718 – 0.0801 |
| Kalman (Q = 0.001) | 0.0873 | 0.0828 – 0.0916 |
| ConvDenoiser (PyTorch) | 0.1101 | 0.1052 – 0.1151 |

Five paired Wilcoxon tests with Holm-Bonferroni correction: the network loses to every filter on all 100 signals (p ≈ 2e-17).

Full tables are in [`results/tables/summary.md`](results/tables/summary.md). They are generated by the code and never edited by hand.

### Why the network loses

It is not undertrained. It ran 381 epochs, validation loss went flat around epoch 284, and it ended 67% better than doing nothing. Three reasons:

- **It has enough capacity.** The winning moving average is a 41-tap kernel. The network's receptive field reaches about 64 samples, so it could represent that solution. It just never found it.
- **The best answer here is almost a straight line.** With Gaussian noise on a smooth signal, the ideal filter is close to linear. A ReLU network spends its capacity approximating something linear and gets nothing back.
- **Deep learning needs a nonlinearity to exploit.** This problem does not have one.

## Three bugs I found and fixed

Each bug produced a result that looked good. That is what made them hard to spot.

| # | Bug | What gave it away | Guard now in place |
|:--|:---|:---|:---|
| 1 | **Data leakage.** I cut the signal into overlapping windows and then shuffled before splitting into train and validation. Almost every validation window had a near-copy in training. | Validation loss sat *below* training loss at every epoch. A 27% lead over Butterworth disappeared on genuinely unseen noise. | `train.py` warns if the pattern comes back |
| 2 | **Phase mismatch.** The network ran non-causally, but three of the five filters still ran causally, so they carried a time lag the network did not. | Removing the lag improved those three filters by 4 to 7 times. That advantage had been handed to the network for free. | `test_zero_phase_mode_removes_the_lag` |
| 3 | **Training noise built from test values.** I generated noise using IAAFT surrogates, which are just a reshuffling of the target's own samples. Confirmed: identical sorted values, spectrum correlation 0.9999. | Nothing. This one never produced a visibly wrong number, which is why it survived two rounds of cleanup. | `make_noise` takes three numbers and no data array, enforced by a test |

**One problem I could not fix:** with no ground truth, the reference curve is a Savitzky-Golay fit — the same approach used in the paper. Scoring smoothers against a smoothed curve is partly circular. On the real recording, a Butterworth filter that knows nothing about the signal closes 44% of the gap to that curve on its own. Fixing this needs a second sensor, so the real-recording table is only a sanity check and the synthetic benchmark is the headline. There the clean signal is genuinely known.

## What this does not show

- **A tuned network.** I grid-searched the five filters. The network's width, kernel size, and learning rate were set once and never searched. That gives the filters an advantage. I doubt a search closes a 71% gap for the reasons above, but I did not run one.
- **Generalisation to other noise.** Training noise and synthetic test noise come from the same generator.
- **Generalisation to other signals.** One rise and fall per curve, always positive. Oscillation, drift, and step changes are out of scope.
- **A verdict from the real recording.** One symptom of the circularity: the Kalman filter finishes *last* among the classical filters on synthetic data and *first* on the real recording.
- **Anything about a second sensor.** There is one recording, of 500 samples.

## Running it

```bash
pip install torch --index-url https://download.pytorch.org/whl/cpu   # the CPU build is not on PyPI
pip install -r requirements.txt

python src/data_prep.py    # builds the reference curve, noise parameters, and the train/test split
python src/train.py        # trains the denoiser, about 2 minutes on CPU
python src/evaluate.py     # tunes every filter, runs the benchmark, writes results/

pytest -q                  # 113 tests, about 2 seconds, no PyTorch needed
```

Run the three scripts in that order. `train.py` needs the noise parameters and `evaluate.py` needs the trained model.

## How the code is organised

Every method, filters and network alike, implements the same `Denoiser` interface: build it, call `apply(signal)`, get a clean signal back. The benchmark loops over a list of denoisers without knowing what any of them does inside, so adding a method means adding a class instead of editing the benchmark.

That is the strategy pattern, and it is also what made the phase fix safe. The forward-and-backward pass lives in the base class, so there is one code path and no method can quietly get a better deal than the others.

```
src/
  filters.py    Denoiser base class and 5 classical filters
  model.py      ConvDenoiser (PyTorch), behind the same interface
  signals.py    synthetic tilt manoeuvre generator
  noise.py      AR(1) noise from parameters only, never from data
  data_prep.py  reference curve, noise fitting, train/test split
  train.py      training loop with leakage and identity-collapse guards
  evaluate.py   tuning, benchmarking, statistics, table generation
```
